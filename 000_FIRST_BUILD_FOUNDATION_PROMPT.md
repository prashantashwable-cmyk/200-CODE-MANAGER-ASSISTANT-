# Prompt 000 — Foundation Build
### Paste this into AI Studio Build mode first, before anything else in this set

---

## What this prompt is (read this before pasting)

Your original brief described the whole business in one pass — every stage, every rule, every screen, all at once, plus instructions like *"so as to no chat required to ai studio... no further development required"*. That instinct (get it right in one shot) is exactly the thing that reliably produces broken, half-working apps with a coding agent, no matter how good the agent is — this is the single most consistent finding across every current write-up on building real software this way, including Google's own guidance on its coding agents. An agent asked to build 200 interconnected screens in one message has to silently guess at priority, sequencing, and how features connect; a human asked to review that output has no way to check it piece by piece either.

So this prompt does **only** one thing: it gets AI Studio to build the **skeleton** — the navigation shell, the role model, the core data model, the design system foundation, and the demo-mode entry point — with placeholder/stub screens where the real screens will later go. Every one of the 200 detailed screens described in your brief then gets built one at a time, in the 200 numbered follow-up prompts included in this set, each one checked before the next begins. Nothing about your original business logic is lost — it's all still here, just sequenced properly.

## The prompt to paste

Build the foundation of a mobile-first, multi-role business platform called **ALL INDIA ELEVATORS COMPANY (AIEC)**, owned by **Mr. Prashant Vasant Wable**. This is Phase 1 of a 20-module, 200-screen build that will happen across many follow-up prompts — **build only what's described below in this prompt. Do not attempt to build out full functionality for every module yet; that comes later, one screen at a time.**

### What AIEC is

AIEC is an asset-light, aggregator-model elevator sales and installation business. It does not own manufacturing or a large employed workforce — it orchestrates independent surveyors, technicians, and elevator suppliers/manufacturers under the AIEC brand, with AIEC as the quality guarantor and orchestrator rather than the asset owner. The intended operating model is **radical automation**: the entire business — from a surveyor finding a construction site, through quoting, negotiating, closing the deal, ordering parts, installing, quality-checking, and handing over to the customer — should run on system-driven workflows with a single person monitoring exceptions, not manually pushing every step forward. Every module built in this project should be designed with that principle in mind: automate the routine, and make the exceptions that need a human impossible to miss.

### Technology foundation

- Build this as a **mobile-first, responsive web application** (works great on a phone browser, installable to the home screen as a PWA, and also fully usable on a desktop browser for the Admin's map-and-analytics dashboard — Admin monitoring genuinely benefits from a larger screen, while surveyors, technicians, and customers will overwhelmingly use this on a phone). This single responsive build serves every role and every device without excluding iOS customers, which a native-Android-only build would.
- Use **Firebase** for backend services (Authentication, Firestore for the data model, Hosting) — set this up now and get Admin approval for the Firebase project before proceeding, since later prompts will depend on Firestore collections already existing.
- Set up **Firebase Authentication** supporting phone number + OTP as the primary sign-in method (India-first), with email/password and Google Sign-In as fallbacks.
- Establish 5 top-level user roles now, even though only Admin and a generic "Demo" experience need to be fully navigable yet: **Admin, Surveyor, Technician, Customer, Supplier**.

### What to actually build in this foundation pass

1. **App shell & routing**: A role-aware navigation shell — bottom tab bar on mobile for each role (tabs will differ per role; for now, stub each role's tab bar with placeholder icons and labels for what will eventually be there, e.g., Admin gets Home/Map/Analytics/Alerts/Settings tabs as placeholders). Desktop should reflow the same navigation into a left sidebar rather than a bottom bar.
2. **Role-based routing logic**: After sign-in, route each account to its correct role's home shell based on a `role` field on the user record. If no role is assigned yet, route to a simple "Pending Approval" placeholder screen.
3. **A minimal Login screen** with a working phone+OTP flow via Firebase Auth, AND a clearly separate "Try Demo" tab/button that bypasses real authentication entirely and loads a seeded demo account for each role (Admin, Surveyor, Technician, Customer) — wire up basic seeded Firestore documents for one sample of each so Demo Mode has something to show. Full detail and polish for this screen comes in Prompt 001 and 002 — for now, just get the underlying routing and the demo-bypass mechanism working end-to-end.
4. **Core data model skeleton in Firestore** — create these top-level collections now, with a minimal set of fields (you will add many more fields to each in later prompts as specific screens need them): `users` (id, role, name, phone, status), `leads` (id, status/stage, surveyor_id, contact info, building info), `deals` (id, lead_id, status, agreed_price), `jobs` (id, deal_id, technician_id, status), `payments` (id, deal_id, stage, amount, status), `suppliers` (id, name, status). Seed 2-3 realistic sample documents in each collection so Demo Mode and early screens have something real to display.
5. **Apply the AIEC design system now**, as the foundation every later screen builds on: import "Fraunces", "Plus Jakarta Sans", and "IBM Plex Mono" from Google Fonts for English text, and "Martel" and "Hind" from Google Fonts for Hindi/Marathi text (neither Fraunces nor Plus Jakarta Sans contains Devanagari glyphs — this second pairing is not optional, it's what stops Hindi/Marathi text silently falling back to an ugly system font the moment someone switches language). Set up every color as a CSS custom property, never a hardcoded hex — `--color-bg`, `--color-surface`, `--color-text-primary`, `--color-text-secondary`, `--color-accent-primary`, `--color-accent-secondary`, `--color-success`, `--color-warning`, `--color-error`, `--color-border` — and define four full token sets for **Light/Alabaster** (default), **Snow White**, **Dark**, and **System**, exactly as specified in the attached design system document. Build one reusable Card component (16-20px radius, soft shadow, gold hairline border) and one reusable primary Button component (gold fill, full-width on mobile) that every later screen will reuse rather than reinventing — both must reference the color tokens, not fixed hex values, so they render correctly in all four theme modes automatically.
6. **Set up the translation (i18n) system now**, before any real screens are built on top of it: use `react-i18next` (or your framework's standard equivalent), with three translation files — `en.json`, `hi.json`, `mr.json` — seeded with the handful of strings this foundation pass itself needs (app name, "Sign In", "Try Demo", role names, "Pending Approval"). Every screen built from this point forward, in this prompt and every one of the 200 that follow, must pull user-facing text from translation keys rather than hardcoding English strings — treat this as a standing rule for the rest of the build, not something to be re-specified prompt by prompt. Language auto-applies the correct font pairing (Latin vs. Devanagari) via a `lang` attribute or language-scoped CSS class.
7. **Add `preferred_language` and `theme_preference` fields to the `users` collection now** (values: `en`/`hi`/`mr`, and `light`/`snow`/`dark`/`system`, respectively), and build a simple language and appearance switcher reachable from Settings — this can be a placeholder/stub location for now, but the fields, the switching logic, and the instant app-wide effect of changing either one must genuinely work from this foundation pass onward.
8. **Build one reusable "Ascension Line" progress component now** — a vertical (or horizontal on wide screens) rail of nodes that fill gold as steps complete, using the `--color-accent-primary` token so it automatically looks correct in every theme mode. This is the app's one recurring signature visual element (echoing the literal product — an elevator ascending floor by floor — as the visual language for every stage-based flow in the app: lead pipelines, installation steps, onboarding wizards, training progress). Build it once, generically, as a shared component now, so every later screen that needs stage-progress UI reuses this exact component rather than each one inventing its own version.
9. **A placeholder home screen for each role** — just enough to prove routing, Demo Mode, language switching, and theme switching all work: after logging in or entering Demo Mode as a given role, land on a simple branded placeholder screen that says which role you're in, with the navigation shell visible around it, and confirm that switching language and switching theme both take effect immediately and correctly on this placeholder. The real, detailed home screen for each role is built properly in the numbered prompts that follow (starting with Prompt 001).

### Code architecture — a standing rule from this prompt onward
For every screen with real state (loading/error/empty/success, form/wizard steps, live data, checklist progress — which is most of them), build it as three small, focused files rather than one large component: **(1)** a types-and-translation-keys file with no logic or rendering, **(2)** a custom hook that owns the state machine with no rendering or hardcoded text, **(3)** a thin view component that reads the hook, renders per state, and pulls all text through `t()` and all styling through the shared design-system components. Full detail and a worked example are in `CODE_ARCHITECTURE_PATTERN.md` — read it now and apply it to every screen from Prompt 001 onward without needing to be told again per prompt. This is the same reason this whole project is built as many small sequential prompts instead of one giant one, applied one level deeper: keeping any single file small enough that quality doesn't degrade as the app grows.

### What NOT to build yet

Do not build the detailed Admin live map, the surveyor lead-capture flow, the quotation engine, the CRM pipeline, or any other specific feature screen described anywhere in the broader brief. Those all come next, one at a time, in the 200 numbered follow-up prompts in this set. If you find yourself writing detailed business logic for a specific screen beyond what's listed above, stop — that belongs in a later, more focused prompt.
